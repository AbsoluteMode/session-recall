# Recall as the registrar's memory: repo attribution, status board, diverse hits

## Контекст

Максим проектирует «Командный центр»: он говорит только с регистратором — LLM-
коннектором, у которого из инструментов один поиск. Регистратор должен отвечать
«что происходит в проекте X», «кто из агентов что делает», «к какому проекту это
относится», «что мы решили по Y», и его память — session-recall. Аудит живого
индекса 25.10 (875 сессий, Qwen3-Embedding-8B) показал, что на эти вопросы recall
отвечает плохо:

- `project` — это папка запуска. Сессия 82ef7c9a числилась `food_sferyx` (запущена
  в его worktree), а сделала 254 файловые операции в `~/harmonia` и ни одной в
  food_sferyx. `recall_search(scope_cwd=~/harmonia)` вернул 2 нерелевантных хита.
  `~/exodia` — симлинк на `~/whytap`, но в индексе это два проекта.
- `recent_sessions.label` — первый промпт, а он часто служебный
  (`<side-sessions-event>` 95 раз, бриф side-сессии 40, `<pasted_content>` 24). Нет
  последнего запроса/ответа, ветки, того, кто открыл сессию.
- «что происходит в проекте Гармония» → 7 из 10 хитов из одной сессии.
- Сниппет — первые 200 символов; у 681 сжатого пересказа это всегда одна и та же
  шапка «This session is being continued…».

## Решение

1. **Атрибуция к репо по вызовам инструментов** (`repos.py`). Каждый путь во
   ВХОДАХ вызовов (Edit `file_path`, `cd`, `git -C`, Codex `workdir`, код Codex
   `exec`) сводится к git-репо: подъём по ФС до `.git`, `.git`-файл worktree ведёт к
   основному чекауту, затем `realpath` (симлинк-псевдоним → один репо). Вызов без
   абсолютного пути засчитывается папке запуска. Чужому репо нужно ≥3 вызова; папка
   запуска засчитывается всегда (если не git — под своим именем). Факты лежат в
   `session_repos` / `session_info` / `repo_scans`, по `file_path`, в той же
   пофайловой транзакции, что и чанки.
2. **`project=` во всех поисковых тулзах** и расширенный `scope_cwd`: сессия
   проходит фильтр, если запущена в репо ИЛИ работала с ним. `scope_cwd` из подпапки
   сводится к корню репо. Anchor получил поле `repos`.
3. **`recent_sessions` как доска статусов**: `label` = первый настоящий запрос
   (из брифа side-сессии — блок `Task:`), `last_user`, `last_assistant`,
   `git_branch`, `repos`, `started_by` (`user` / `agent` / `automation`), `active`.
4. **Не больше 2 хитов на сессию** в `recall_search` (`per_session`, 0 = выкл.), с
   добором в порядке ранга, если сессий меньше, чем слотов. Реранкер теперь
   упорядочивает все кандидаты, а не top-k.
5. **Сниппет по запросу** (`snippets.py`): окно, покрывающее больше всего слов
   запроса (префиксное совпадение — «Гармония»/«Гармонии»), шапка compaction-
   пересказа срезается; без буквального совпадения — начало текста.

## Почему

- Вызовы инструментов — единственное надёжное свидетельство, с каким кодом
  работала сессия; текст ответа упоминает чужие репо постоянно, а результаты
  инструментов (листинги, `ls ~`) — тем более, поэтому учитываются только входы.
- Скан — только текст, без эмбеддингов: старый индекс догоняется одним потоковым
  проходом, без повторной оплаты эмбеддера и без смены `EXTRACTOR_VERSION`.
- `started_by` берётся из метаданных (`entrypoint` у Claude, `originator`/`source`
  у Codex), а не из слов: промпт подделать легко, метаданные — нет. Две текстовые
  формы (бриф side-сессии, `<heartbeat>`) — то, что оставляет сама программа.
- Лимит на сессию с добором: регистратору нужен разрез по сессиям, но узкая
  история не должна возвращать меньше k.

## Что протестировали

- `tests/test_registrar.py` — сценарии из живого индекса: сессия в worktree
  одного репо правит другой; симлинк-псевдоним; «взгляд» на соседний README и
  чтение плагин-кэша (git-клон в `~/.claude`) не дают атрибуции; удалённый
  worktree и не-git папка; scratch-папка в `~/Library`; Codex `workdir` + код
  `exec` + `originator: Claude Code`; догон старого индекса без единого нового
  эмбеддинга; рост и удаление транскрипта; доска статусов с брифом,
  `<side-sessions-event>`, `<pasted_content>`, heartbeat, `sdk-cli`; лимит на
  сессию и добор; сниппет у compaction-пересказа; проброс `project` через MCP и
  клиент хаба.
- Первая версия `grep` с фильтром `project` молча теряла все хиты: локальная
  переменная цикла перезаписывала параметр `project` — поймал существующий тест
  Codex-интеграции.
- `scope_cwd` из подпапки (`~/harmonia/src`) сначала не находил работу из других
  папок: сравнивался путь, а не корень репо. Исправлено отдельным подъёмом до
  `.git` без фильтров атрибуции.
- Первый прогон на клоне живого индекса завис на первом же транскрипте: хвост
  URL `https://github.com/…` распознавался как путь `//github.com/…`, а POSIX
  `dirname("//") == "//"` — подъём к корню не кончался. Плюс `repo_of("/")` через
  `normpath("")` превращался в `.` и находил репо текущего каталога. Оба случая
  закрыты и покрыты тестом; после фикса тот же транскрипт сканируется за 0.01 с.
- Второй прогон показал дыру: Codex держит worktree в `~/.codex/worktrees/<id>/<repo>`,
  а скрытые папки отбрасывались до поиска `.git` — 44 сессии whytap остались без
  атрибуции. Теперь скрытая папка судится по репо, к которому ведёт (worktree →
  основной чекаут засчитывается, git-клон плагина в `~/.claude` — нет), а удалённый
  Codex-worktree сводится к одноимённому чекауту в `~`. После этого 0 сессий
  whytap/exodia без атрибуции.
- Клон живого индекса (876 сессий, 620 транскриптов, 6.8 GB): догон фактов —
  25 с, без единого нового эмбеддинга. whytap: 224 сессии (было 89 + 136 под
  двумя именами); harmonia: 5 сессий вместо 1; 4 сессии «food_sferyx» на деле
  работали в другом репо; `started_by`: 451 user / 177 agent.
- Живые запросы: «что происходит в проекте Гармония» — 6 разных сессий в топ-10
  вместо 4 (7 хитов было из одной); `scope_cwd=~/harmonia` находит работу из
  worktree food_sferyx вместо двух нерелевантных хитов. Локальная часть поиска
  (knn+fts) — 0.8 с против 1.0 с до изменений; реранк 100 кандидатов не дороже 10.

## Отвергли

- Определять проект по тексту (упоминания имени репо) — шум: MEMORY.md с именами
  всех проектов вставлен в каждую сессию.
- `git remote` вместо пути — нужен `git` на каждый путь и не работает на хабе.
- Переписать `chunks.project` — пришлось бы перевыпускать весь индекс и ломать
  смысл поля «где запущено», на который опираются старые клиенты.
- Отдельная тулза `project_state` — следующий шаг поверх атрибуции (пункт 6
  аудита), не в этом PR.
- Чистка шума в `grep` (пункт 5 аудита) — отдельным заходом.

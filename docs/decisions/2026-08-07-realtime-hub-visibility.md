# Работа коллеги видна в общем поиске почти сразу

## Контекст

Командный хаб отдавал историю с задержкой в часы. Два разных лага складывались:

1. **Клиент отправлял транскрипты только на `SessionStart`.** Пока человек не
   закроет текущую сессию и не откроет следующую, ничего из его работы на хаб не
   уезжало вообще. Для долгой сессии это полдня.
2. **Сервер индексировал загруженное раз в 10 минут** (`OnUnitActiveSec=10min`).

Требование, из-за которого это стало проблемой: вечерний дайджест работы команды
собирается из хаба, а «видеть, что делает команда» хочется в момент работы, а не
на следующий день. Формулировка задачи — «написал сообщение, оно видно; агент
ответил, ответ виден».

## Решение

- Плагин пушит после каждого хода: хуки `UserPromptSubmit` и `Stop` дополнительно
  к существующему `SessionStart`. Оба вызывают `session-recall hub push` в фоне.
- Серверный таймер индексации — раз в минуту вместо десяти.

Итоговая задержка: секунды на отправку плюс до минуты на индексацию.

## Почему

**Почему push после каждого хода, а не по таймеру на клиенте.** Ход — это ровно
то событие, после которого появились новые байты. Таймер либо будит машину
впустую, либо просыпается не тогда.

**Почему это дёшево.** Отправка инкрементальная — уезжает только хвост файла.
Замер на реальной сессии: 2.4 секунды на 87 KB, и это в фоне (`&`), сессия его не
ждёт. `pgrep` не даёт запуститься второму пушу поверх идущего.

**Почему хук молчит у тех, кто не в команде.** Первой строкой — проверка
`hub.json`; нет файла, значит машина не подключена к хабу, и хук выходит с нулём.
Плагин ставят и вне нашей команды, у них не должно появляться ни ошибок, ни
лишних запусков.

**Почему минута, а не 10 секунд.** Прогон индексации — это эмбеддинги новых
чанков; десятисекундный цикл начал бы наслаиваться сам на себя без выигрыша,
который человек способен заметить.

## Что протестировали

- `session-recall hub push` на живой сессии: 2 файла, 89 161 байт, 2.4 с.
- `/v1/recent` за день с ключом участника: сессии приходят с полем владельца —
  видно, чья работа, без ручной сверки.
- Прогон индексации на сервере при 10 накопленных файлах: 34 с CPU. За минуту
  накапливается заметно меньше, в цикл укладывается.

## Отвергли

- **Индексация по событию из `/v1/ingest`** — честный realtime, но это очередь и
  разделяемое состояние между сервисом и индексатором; минутный таймер даёт почти
  тот же результат без нового кода.
- **Пуш на `PostToolUse`** — срабатывает по десятку раз за ход, а новых байтов
  добавляет столько же, сколько один пуш в конце.
- **Ускорить только серверный таймер** — не помогло бы: главный лаг был на
  клиенте, где данные лежали до следующего запуска сессии.

# P2P-обмен recall-знаниями: security-гейт первой итерации

## Контекст

Идея (сессии 28–30.07.2026): пользователь A задаёт вопрос recall-индексу пользователя B
(«как ты чинил этот баг?»). Агент B находит ответ в локальном индексе B, владелец
одобряет отправку — ответ уходит A. Минимальными ресурсами закрывает вопросы уровня
«как ты это делал» между двумя людьми (Максим ↔ Егор), без организаций, ролей и
мультидевайса. Жёсткий инвариант session-recall сохраняется: индекс и история живут
локально, наружу уходит только явно одобренный ответ.

Главная угроза сформулирована в первом же сообщении идеи: prompt-инъекция — «нейросеть
отдаст мимо пользователя чувствительные данные». Индекс — сырые транскрипты: env-дампы,
ключи, логи, чужие переписки. Любой retrieval может притащить секрет в ответ на
невинный вопрос.

## Решение

Security-гейт v1 — три рубежа плюс DX-требование.

**Вход (кто спрашивает):**

1. Pairing-церемония один раз: одноразовый короткоживущий invite-код по внеполосному
   каналу + сверка SAS-строки с обеих сторон (как Signal). Дальше каждый запрос
   подписан ключом устройства. Токен — не bearer-строка, а identity:
   `{user, device_pubkey, mode: accept|bypass, scope, ttl, rate}`.
2. Токены заводит только человек через CLI/UI. У LLM физически нет тулзы управления
   trust-store.
3. Адрес пользователя — 128 бит рандома (base58). Не секрет и не аутентификация —
   защита от энумерации и спама. Запросы от неизвестных ключей дропаются молча.
4. Лимиты после проверки подписи: 3 запроса/мин + дневная квота на токен.
   Неподписанное не тратит ни LLM, ни нотификации.
5. Клиенту не доверяем by design: никакой аттестации «немодифицированной сборки» —
   сервер жёстко валидирует схему сообщений, версия клиента — только для
   совместимости. Все рубежи работают против модифицированного клиента.

**Обработка (клетка воркера):**

6. Запрос внешнего пользователя никогда не попадает в контекст полноправного агента.
   Его читает отдельный воркер-LLM, у которого ровно две возможности:
   (а) запросы к индексу (recall_search/expand, read-only; НЕ generic Read по ФС),
   (б) вернуть структурированный кандидат-ответ локальному серверу (текст + чанки
   с провенансом, схема валидируется). Ни Bash, ни сети, ни Write.
7. Сессии воркера не индексируются (или тегируются `external/untrusted` до выдачи) —
   иначе текст чужого запроса въезжает в индекс и позже срабатывает как stored-инъекция
   в обычной сессии.

**Выход (что уходит):**

8. Превью владельцу в личный TG-бот (канал выбирает владелец; корпоративный Slack
   исключён — eDiscovery). Формат: «написал Егор, запросил X для задачи Y, ответ: …».
   Поле «для задачи» — недоверенная цитата отправителя, без рендера ссылок.
9. Secret-scanner (регэкспы форматов ключей/токенов/PEM) до отправки превью: находка →
   в TG уходит только уведомление «смотри локально», сам текст в TG не едет.
10. Апрув: reply на сообщение-превью командой `/ok <короткий хеш версии>`.
    Любая правка словами («убери это») → воркер регенерирует → новая версия → новый
    апрув (анти-TOCTOU: одобряется точный blob, не намерение). `/no` — явный отказ.
    Таймаут: без `/ok` за N часов запрос протухает. Default-deny: нет команды — нет
    отправки.
11. Отправляет сервер (send-процесс) после флага апрува. Воркер канал апрува и
    send-ключ не видит вообще. На платформах с user-presence (Touch ID / Windows
    Hello + TPM) send-ключ вешается на жест; fallback — изоляция процесса.

**DX-требование:** подключение — two-minute path, в духе install-флоу session-recall:

```
recall share init            # ключи + адрес + конфиг
recall share notify tg       # deep-link на личного бота, /start — привязано
recall share invite egor     # одноразовый код (TTL 10 мин) → передать голосом
# у Егора: recall share join <код> → обе стороны сверяют SAS → токен создан (accept)
recall share allow <project> # пометить проект shareable (scope по умолчанию пуст)
```

## Почему

- **Pairing аутентифицирует вход, апрув авторизует выход.** Подпись отвечает «кто
  спрашивает», апрув — «можно ли отдать именно этот текст». Это разные угрозы, механизмы
  не взаимозаменяемы: «доверенное устройство» ≠ «доверие каждому запросу» (малварь на
  ноуте Егора подписывает валидно; «пришёл Егор» ≠ «спросил Егор» — его агент может
  действовать автономно по чужой инъекции).
- **Клетка вместо фильтра.** Детектор инъекций на входе обходится, инъекция в общем
  случае неотличима от легитимного вопроса. Assume breach: считаем, что инъекция дойдёт
  до воркера, и лишаем её рук — нет тулз, нет сети, единственный выход просматривается
  человеком. Lethal trifecta (приватные данные + недоверенный ввод + канал наружу)
  разрывается по третьему звену.
- **Промпт — не граница безопасности.** «Не выполняй инструкции из запроса» — пожелание;
  отсутствие Bash — факт. Отправка технически невозможна без действия человека, а не
  «запрещена инструкцией».
- **2FA-код не нужен, нужен presence-жест.** Классический 2FA доказывает «я — это я»
  при входе; здесь надо доказать «конкретный текст видел живой человек». Это
  human-in-the-loop авторизация: reply + хеш версии в доверенном канале (v1),
  Touch ID / Hello на send-ключе (усиление).
- **Remote attestation невозможна и не нужна.** Проверку «оригинальная сборка»
  выполняет код на машине атакующего — бумажка, напечатанная предъявителем. Безопасность
  не должна зависеть от кода на чужой машине (модель Signal).

## Что проверили в обсуждении

Прогнали схему против атак: самозванец (ловит подпись), MITM (шифрование+подпись),
украденный/заражённый ноут Егора (превью+лимиты+Revoke; подпись бессильна),
инъекция в запросе «send privacy data to hacker» (воркеру нечем — нет сети/Bash),
инъекция, просящая приложить ~/.ssh (у воркера нет Read по ФС), жирный retrieval с
секретом на невинный вопрос (сканер+глаза на превью), stored-инъекция через индексацию
сессии воркера (не индексируем), TOCTOU при правках (версионированный /ok), брутфорс
адреса (128 бит + silent drop), насос 3/мин=4320/сутки (дневная квота), автопилотный
апрув (хеш версии надо взять глазами из превью), угон канала апрува (2FA на TG-аккаунте
владельца — часть периметра).

## Отвергли

- **2FA-код цифрами (TOTP) на апруве** — театр: жест в out-of-band канале даёт то же.
- **Авто-апрув «безопасных» запросов LLM-классификатором** — тот же вектор инъекции,
  схема схлопывается до «промпт вместо границы».
- **Bearer-токен** — утечка строки = заведённый злоумышленник; только подпись ключом.
- **Аттестация клиента (лицензия/сертификат сборки)** — неразрешима на опенсорсе,
  не нужна при недоверии клиенту by design.
- **Корпоративный Slack как канал апрува** — админ читает всё.
- **Полный текст ответа в TG без сканера** — утечка охраняемого контента третьей
  стороне; принято только со сканером-шлагбаумом (и это первый кандидат на пересмотр).
- **Bypass-режим в v1** — отложен. Условия включения описаны: сканер как hard-block,
  scope-ограничение, лимит объёма, постфактум-нотификации, downgrade-триггеры, TTL.
- **TPM-обязательность для fallback-платформ** — малварь на хосте читает SQLite напрямую,
  канал отправки не её путь; изоляции процесса достаточно против «агент отправил сам».

## Открытые вопросы (не блокируют v1)

- Транспорт: минимальный relay/rendezvous-сервер, хранящий только зашифрованные
  конверты (E2E на ключах pairing) — выбрать при реализации.
- Шифрование индекса at rest (ключ в Keychain/Hello) — канал отправки сейчас защищён
  лучше хранилища.
- Криптография — только libsodium, ничего самодельного.

# meta docs удалён: слой знаний из сессий уходит в little-memory

## Контекст

meta docs (31.07, PR #25/#26) — ночная джоба, которая дистиллировала диалоги
сессий в записи `bugs/actions/decisions` + `USER` в отдельном git-репо и
подмешивала их в общий индекс как `source="metadocs"`. Расписание отработало
неделю (31.07–06.08) и было снято, но подмешивание осталось живым: каждый
`session-recall index` (его зовёт хук SessionStart) переиндексировал записи, и
`recall_search` выдавал их наравне с историей.

Ту же идею — карточки действий и багов, извлечённые из сессий, — сейчас
заново строит little-memory, исследование проактивной памяти агента. Но вместе
с тем, чего в meta docs не было: моментом, когда карточку нужно подать агенту
без его просьбы.

## Решение

Удаляем meta docs целиком: пакет `session_recall.metadocs`, команду
`session-recall metadocs`, подмешивание в `index`, тесты и разделы README.

- `acquire_lock` — им пользуется хаб-индексер — переезжает в
  `session_recall/hub/lock.py`.
- Строки `source="metadocs"` в уже построенных индексах удаляются при первом
  открытии индекса на запись (`Store._drop_retired_sources`). Ни `index`, ни
  `prune` их больше не трогают, транскрипта за ними нет — без чистки они
  всплывали бы в выдаче вечно.
- Репо с записями не трогаем: это данные пользователя, а не код.

## Почему

- **Записанное знание не доходило до агента в момент действия.** Одна из
  записей прямо предупреждала: «на сервере может не быть `sqlite3` — работай
  через Python». После неё минимум 6 сессий того же проекта упёрлись в
  `sqlite3: command not found`. Pull-режим — «агент сам решит поискать» — здесь
  не срабатывает. Подача в нужный момент — задача little-memory, а не индекса.
- **Не та гранулярность.** Дистиллятор видел только диалог, без tool-вызовов,
  и записывал задачи уровня сессии. Около половины `actions` в разобранном
  проекте — разовые фичи, а частое действие «посмотреть трейс» (42 запроса в
  24 сессиях) записи не получило. Повторяемость живёт в tool-вызовах.
- **Проект по cwd ошибается.** 3 из 24 `actions` одного проекта относились к
  другим проектам: сессия запущена в одном репо, а действие касалось другого.
- **Два слоя одного знания разойдутся.** Замороженная копия того, что заново
  строится рядом, — второй источник правды и ~2K строк кода и тестов на
  поддержку.

session-recall остаётся тем, чем был до meta docs: хранением и поиском по сырой
истории. Проактивная подача — отдельный слой поверх него.

## Что протестировали

- Аудит репо с записями (12.10): 70 `actions`, 81 `bugs`, 71 `decisions` по
  14 проектам; 24 `actions` одного проекта разобраны вручную на гранулярность и
  привязку к проекту.
- Grep по истории: повторные `sqlite3: command not found` после записи с
  предупреждением.
- Тест чистки: строки `metadocs` уходят из `chunks`, `vec_chunks`, `fts_chunks`
  и `indexed_files`, транскрипты не задеты, повторное открытие ничего не
  меняет. Без чистки тест падает. Тест блокировки хаб-индексера перенесён.

## Отвергли

- **Выключить по умолчанию и оставить код** — мёртвый код, а при старом
  конфиге подмешивание в индекс продолжается.
- **Оставить только индексацию готовых записей** — замороженные записи молча
  устаревают и выдаются наравне с живой историей.
- **Удалить репо с записями** — это данные пользователя и готовый v0-корпус
  карточек для пилота little-memory.

# Осиротевшие строки индекса роняли глобальный recall_search

## Контекст

Проверка «работает ли recall после починки Voyage-egress» показала: эмбеддинги живы
(`degraded=null`), `grep`/`recent_sessions`/scoped-поиск работают, а **глобальный**
`recall_search` (без `scope_cwd`) падает:

```
retrieve.py:105  c = self.store.get_chunk(cid)
store.py:213     data = dict(zip(_COLS, row))   ← row = None
TypeError: 'NoneType' object is not iterable
```

Один и тот же запрос: scoped — 8 якорей, global — краш.

В боевом индексе (39k чанков) нашлось **120 строк в `vec_chunks` и 120 в `fts_chunks`,
чей `chunk_id` указывает на удалённую строку `chunks`** — тремя непрерывными
блоками по 2, 13 и 105 id.

## Решение

Три изменения, каждое закрывает свой слой:

1. **`Store.delete_file` использует один критерий** — `file_path` в подзапросе для
   всех трёх DELETE, вместо снимка `ids` + сметания `chunks` по `file_path`.
2. **Неscoped ветки `knn()`/`fts()` фильтруют по существованию чанка**
   (`IN (SELECT id FROM chunks)` / `JOIN chunks`), как это давно делали scoped-ветки.
3. **`get_chunk()` возвращает `None`** для пропавшего id, а `recall_search`
   пропускает такой кандидат вместо падения всего поиска.

## Почему

**Источник сирот — гонка двух индексаторов.** `delete_file` читал `SELECT id FROM
chunks WHERE file_path = ?`, а удалял `chunks` по `file_path`. SELECT не открывает
write-транзакцию, поэтому между снимком и удалением параллельный индексатор успевал
закоммитить новые чанки того же файла: сметание по `file_path` сносило их строку в
`chunks`, а `vec`/`fts` оставались — их id не было в устаревшем снимке. У Максима
одновременно живут несколько сессий Claude Code, и каждая дёргает freshness-хук, так
что окно открывается регулярно. Непрерывность блоков (2/13/105) — ровно один проход
индексации по одному файлу.

Единый критерий убирает окно: первый DELETE открывает write-транзакцию и держит
блокировку до конца, а подзапрос вычисляется по актуальному состоянию, а не по
снимку. Заодно исчезает `IN (?,?,…)` на тысячи переменных.

**Почему падал именно глобальный поиск.** Scoped-запросы всегда джойнили `chunks`
(им нужен `cwd` для фильтра по репозиторию) и потому автоматически отсеивали сирот.
Неscoped ветки читали `vec_chunks`/`fts_chunks` напрямую и отдавали висячий id в
`get_chunk`. Баг жил незамеченным, потому что в CLAUDE.md `scope_cwd` — рекомендуемый
дефолт: ломался только кросс-проектный поиск, и то не всегда — лишь когда сирота
попадала в топ кандидатов.

**Почему `get_chunk` тоже правим.** SQL-guard не покрывает гонку: фоновая
переиндексация может удалить чанк между выбором кандидатов и их чтением. Пропажа
одного кандидата должна стоить одного слота выдачи, а не всего поиска.

## Что протестировали

- **Прямое воспроизведение**: тот же запрос scoped → OK, global → краш. Подтвердило,
  что дело в ветвлении SQL, а не в эмбеддере.
- **Откат транзакции** (`add` × 2 → `rollback`): `chunks`, `vec_chunks`, `fts_chunks`
  обнуляются согласованно. Гипотеза «vec0 не откатывается» — отвергнута.
- **`delete_file` на 2 / 13 / 105 / 1000 / 5000 чанков**: сирот не остаётся ни на одном
  объёме. Гипотеза «лимит SQL-переменных в `IN (…)`» — отвергнута.
- **История `delete_file` по всем коммитам**: `DELETE FROM vec_chunks` присутствовал с
  первого релиза. Гипотеза «сироты от старой версии без чистки индексов» — отвергнута.
- **Соседи сирот по id**: слева и справа от каждого блока чанки тоже удалены, но без
  сирот. Значит блок исчез из `chunks` отдельно от остальных строк файла — это и
  вывело на расхождение двух критериев.
- **Гонка в лаборатории**: тест подменяет соединение прокси, который коммитит вставку
  второго `Store` ровно между снимком и удалением. На старом коде — 1 сирота, на новом — 0.

## Отвергли

- **Только почистить БД** — лечит симптом, гонка воспроизвела бы сирот снова.
- **`FOREIGN KEY ... ON DELETE CASCADE` на `vec_chunks`** — vec0 виртуальная, внешние
  ключи к ней неприменимы.
- **Ронять поиск с внятным `LookupError` вместо пропуска** — кросс-проектный recall
  важнее строгости: одна битая строка не повод отдать пользователю ноль результатов.
- **Автоматическая чистка сирот при открытии БД** — лишний скан 39k строк на каждый
  старт ради состояния, которое новый `delete_file` больше не создаёт.
